Jev router / revised 2026-09-28 / proposed, not implemented

One router. One recipient.
A reply you can track.

Keep a small, always-on process between senders and their Paseo or herdr peers. Jev chooses who owns an unaddressed request. The router records the delivery outcome and makes the recipient's explicit reply available to the sender.

The useful simplification is one routing decision and one task record shared by both delivery paths.

Recommended design

One process, one A2A endpoint, one local task journal. Keep the peer roster in memory. Use one Jev Choice for unaddressed requests and zero model calls for addressed messages, replies, or continuations. Deliver through one adapter per system.

Ship a complete local Paseo request-and-reply path first, using the same A2A contract that later supports herdr and remote callers. Add semantic routing after that path works. Completion, duplicate handling, and an uncertain send outcome belong in the first usable version.

1. Evaluation: keep the shape, tighten the contract

The original proposal puts judgment in a sensible place: between a shared roster and native delivery. Its main weaknesses are unnecessary model decisions and missing delivery semantics. These are design findings, not measured runtime failures.

Original design Problem Revision
Recipient + intent + escalation questions Intent is already known for a reply. “Blocked” can mean a peer needs help; it does not always require a human. Ask only who owns a new request. Message kind is explicit. The receiving agent retains its existing approval rules.
Global status drives task progress A running, idle, or blocked agent may be handling unrelated work. A prompt receipt cannot supply the missing result. Use task-scoped replies for progress and completion. Native state only informs availability.
Task table without recovery rules A restart can lose the sender, result, or deduplication record. A timeout followed by direct fallback can submit work twice. Persist task and message receipts before delivery. Surface uncertain outcomes without resending.
A2A first in the architecture, last in rollout The first CLI would need a temporary contract and a later rewrite. Use one A2A HTTP binding from the first working slice. Defer extra transports, streaming, and push notifications.
Live discovery and full hierarchy up front Subscriptions, joins, and reconnect handling add work before the request-and-reply path is proven. Start with explicitly registered peers and background snapshot refresh. Add subscriptions only when freshness requires them.
“Recipient selection is the biggest cost” No stage timings support that ranking. One exchange would not establish it either. Keep the user's Jev speed premise. Instrument the working path; treat end-to-end savings as an open measurement.

Keep the ordinary process, explicit sender calls, host-qualified identities, native adapters, and a no-match outcome. Leave broadcast, automatic forwarding, and a separate directory process out of the initial scope.

2. One owner for routing and task state

Memory: the routing roster

Merge approved registrations with observed presence. Each peer needs a stable key, session identity, scope, responsibility, native target, availability, and observation time. Start from a small configuration file; titles and terminal text cannot enroll a peer.

Use an encoded tuple of system, host, and full native ID. Pin the agent session as well as the herdr pane; a replacement agent must register again.

Disk: tasks and message receipts

One local SQLite journal owns the requester, chosen peer/session, original text, task state, delivery outcome, reply, and received message IDs. The roster can be rebuilt; accepted work must survive a restart.

This persistence is a proposed addition. It avoids moving recovery and duplicate prevention into every caller.

The router module owns lifecycle, policy, and storage. Each delivery adapter hides native discovery and submission behind two operations: snapshot() and deliver(peer, envelope). Delivery returns accepted, not_sent, or unknown; exceptions must be translated into one of those outcomes.

Deployment default: start on this Linux host with local Paseo peers, an authenticated loopback endpoint, and no automatic service installation. When adding herdr, run beside its socket. Admit remote peers only after they can reach the router for replies using an authenticated network endpoint.

3. A small interface that closes the loop

The proposed CLI has three everyday commands. It wraps A2A SendMessage and GetTask; senders do not need to learn native delivery or Jev's response shape. 

# New request; add --to for an exact registered peer.
route send --scope jev-a2a --file request.txt

# Read the receipt or wait for input-required / a terminal result.
route status TASK_ID --wait

# Receiver explicitly returns the result.
route reply TASK_ID --in-reply-to MESSAGE_ID --state completed --file result.txt

# Sender answers a peer's question on the same task.
route send --task TASK_ID --in-reply-to QUESTION_ID --file answer.txt

# Sender resolves an ambiguous recipient; original text is reused.
route send --task TASK_ID --in-reply-to QUESTION_ID --to PEER_KEY
  • Message identity: the CLI allocates and prints a message ID before sending; --id reuses it after a connection failure. Each new reply or continuation has its own ID. The task ID is assigned once by the router.
  • Caller identity: authentication binds the requester or registered peer. A from field in message text cannot establish identity. Task reads are scoped to authorized participants; only the assigned session can report receiver progress.
  • Receiver participation: enrollment proves that the peer can invoke route reply. The delivered envelope contains the task ID, delivered message ID, original text, and reply instructions. Each reply's inReplyTo identifies that delivered message. This receiver integration is part of the first implementation.
  • Reply meaning: started, input_required, completed, and failed are explicit updates. A question leaves the task open; its update message ID is the question ID. Router-generated routing prompts use the same convention. A final result for the current exchange ends the task. Task IDs alone never imply completion.
  • Result retrieval: the result stays in the journal if the sender disconnects. --wait polls and returns on a question or final state; it does not inject a new prompt into the sender's terminal. Poll again after reconnecting.
Where the router's contract extends A2A

Use one router Agent Card and one HTTP binding. The SDK owns wire validation. Text, message IDs, task IDs, and polling use standard A2A fields. A versioned metadata.jevRouter object carries scope, optional recipient, operation, reply state, and inReplyTo. These are proposed router-specific fields, not built-in A2A routing features.

Document that metadata contract in the Agent Card's extension information. A plain client can submit a text request using its configured default scope and poll for a result. Registered receivers use the CLI or that extension to post task updates. The router authenticates the caller before interpreting an update.

Sender continuations use message.taskId. Receiver callbacks and operator resolutions instead omit that field, identify exactly one task in referenceTaskIds, and receive a direct Message receipt. Their explicit operation bypasses routing and task creation. This lets the router record late evidence while respecting A2A's rejection of new messages addressed to terminal tasks. Current final results are exposed as task artifacts; authorized task reads also include recorded late evidence.

Serve required core read/list operations from the same journal. Disable streaming and push capabilities initially. Return TaskNotCancelableError unless the adapter can stop that specific work; never cancel a peer's whole active turn by inference. A2A operations and task model.

4. One semantic decision, with an abstention

  1. Validate and deduplicate. Authenticate, enforce the caller's scope, validate input limits, and look up the message ID before any model or delivery call.
  2. Use known destinations. Explicit to, replies, and existing-task continuations skip Jev. Outbound delivery requires authorization and fresh presence. Inbound replies require current authentication/authorization and the task's persisted assigned-session identity; stale discovery cannot invalidate a legitimate reply. An invalid explicit target never falls back to semantic routing.
  3. Construct the choices. Include registered peers in the authorized scope, plus none. Keep ownership separate from readiness: a busy or temporarily offline owner can still be selected, then reported unavailable. Do not substitute an idle peer just to get a send away. With no registered peers, skip Jev and return input_required; enrollment must precede an explicit recipient choice.
  4. Ask Jev once. Supply only the request and responsibility descriptions. Even one peer competes with none. If the scope still exceeds 254 peers, require a narrower scope or an explicit target.
  5. Apply policy, then revalidate. A valid choice above the configured threshold can proceed. Re-resolve its registered session and current presence immediately before attempting delivery.

Use confidence ≥ 0.9 as a provisional prototype setting, evaluated against labeled routing examples. Confidence describes the distribution of choices; it is not a measured probability that the workflow is correct, nor permission to perform the requested work. TypeSafe confidence guidance.

Condition Behavior
Explicit, authorized target Skip Jev; check the pinned session and availability. Addressing changes selection, not permission.
Choice passes the threshold Freeze one recipient, reserve it for this task, and attempt delivery after a fresh check.
No match or low confidence Return input_required with reason choose_recipient and authorized suggestions. The sender can name one peer on the same task. Never send to multiple suggestions.
Chosen peer is busy, stale, or gone Refresh once without sending. If still unavailable, return a definite not_sent outcome. New work is rejected with the reason; an existing task's continuation remains pending for its sender.
Jev unavailable or malformed output Use a bounded request deadline; any transport retry stays within it and occurs before delivery. If no valid answer arrives, return input_required so the sender can supply a target.
External routing disabled for this scope Require an explicit recipient. The request never goes to TypeSafe.

The router supplies only authorized choices. Message content can still manipulate selection or influence a recipient, so typed output does not remove prompt-injection risk. Existing receiver permissions remain authoritative.

Illustrative Jev request - one Choice question

Send this shape to POST https://api.typesafe.ai/v1/systemone, with authentication held by the router. The peer keys and descriptions are examples. Request contract; Choice behavior and limits. 

{
  "model": "jev-latest",
  "state": {
    "scope": "jev-a2a",
    "message": "Review the router diff for correctness."
  },
  "questions": {
    "recipient": {
      "type": "choice",
      "instructions": "Which registered peer owns this work? Choose by responsibility. Choose none if the request has no clear owner or lacks enough context.",
      "criteria": {
        "p0": "Reviews jev-a2a diffs and reports findings.",
        "p1": "Implements requested jev-a2a features and fixes.",
        "none": "No listed responsibility clearly matches."
      }
    }
  }
}

The response's choice key maps to the exact peer and session in the request snapshot. Validate the returned answer and probabilities; never treat an answer as a native ID or command. Record the returned model version and policy version for diagnosis. Do not add unused intent or escalation questions.

5. Delivery, replies, and recovery

The guarantee is at most one automatic delivery attempt per accepted message. Repeated submissions return the recorded outcome. Native delivery does not establish exactly-once execution, and a missing acknowledgment must remain visible.

Before delivery

Atomically record the authenticated sender, message ID, payload hash, and task. Reusing the ID with different content is an error. Concurrent copies join the same record.

Commit the selected peer/session and attempting before calling the adapter. If persistence fails, do not send. Reserve at most one open router task per peer; its own continuations reuse that reservation. Do not add a queue in the first version.

After delivery

accepted means the backend accepted input. not_sent requires evidence that no input was submitted. A timeout, disconnect, or crash during the attempt produces unknown.

A valid reply resolves only the attempt identified by inReplyTo. A delayed update for an earlier message is retained as history and cannot advance the current exchange or release its reservation. Adapter acknowledgments follow the same rule and cannot overwrite newer replies or finished task states. Within one delivery, started cannot overwrite an outstanding question or a final result.

Task state Evidence required What the caller can do
Submitted The router durably accepted the request. Backend acceptance is recorded separately. Read or wait for the task. This receipt is not proof that the peer has started.
Working The assigned session posts a task-scoped started update. Wait or poll. A peer's global “working” status is insufficient.
Input required A routing choice is unresolved, the peer explicitly asks a question, or delivery is uncertain. The reason determines the action: choose a recipient, answer the pinned peer, or inspect uncertain delivery. An uncertain send cannot be retried through a continuation.
Completed / failed The assigned peer sends a final result, or the router reaches its task deadline and records failure. Retrieve the result or precise failure reason. A deadline does not mean the underlying work stopped.
Rejected The router declines new work before delivery, for example because the chosen peer is unavailable. Fix the cause, then explicitly start a new attempt with a new message ID.

These are proposed mappings to A2A task states. Delivery outcome is a separate field. Use the chosen SDK's actual enum values when implementing. A2A task-state definitions.

  • Resume only the expected action. A recipient choice reuses the stored request; a peer question forwards the sender's answer to the existing recipient. Both quote the outstanding question ID from task status. Atomically consume that question when accepting a continuation; concurrent or stale answers with different message IDs fail instead of sending twice. Serialize updates per task and allow only one outstanding question. No continuation changes a delivered task's recipient. Recheck current authorization. If an answer is definitely not_sent, reopen the question so the sender can explicitly retry with a new message ID.
  • Recover conservatively. Reload the journal on restart. An unfinished attempting record becomes unknown and is not replayed. A never-attempted message can resume after fresh validation. Repeated message IDs never initiate another delivery.
  • Keep uncertainty visible. Unknown delivery or a deadline after submission retains the peer reservation until an authorized operator reconciles it or a valid final reply proves that work ended. Record that resolution; do not release the peer just because it appears idle.
  • Preserve final states. Deduplicate replies too. Store late results for the requester to inspect, but do not reopen terminal tasks. A late valid final reply to the latest outstanding delivery may resolve its reservation without rewriting task history.
  • Make fallback deliberate. Direct sending is safe only when the router definitely never accepted the request or records not_sent. A client timeout alone is insufficient. Read the receipt first; never automatically reroute an uncertain send.
  • Bound resource use. Limit message size, active tasks, and wait deadlines. Keep task and deduplication records for the prototype's lifetime; reject new work on capacity or disk errors. Define retention before unattended production use.
Operator recovery for an uncertain task

A separate operator-only command, route resolve TASK_ID --in-reply-to MESSAGE_ID --outcome finished --file evidence.txt, records a manual reconciliation after checking the native peer. The allowed outcomes are not_sent and finished. It never sends the request again. It clears the reservation and closes a still-open task as failed with the resolution attached; an existing terminal state stays unchanged.

The endpoint requires an operator identity and an idempotent message ID. Its message reference must match the currently unresolved delivery. It uses the callback metadata contract above. Ordinary peers cannot use it. If work may still be running, leave the task unresolved. This recovery command is required in the first usable version so uncertainty does not create a permanent lock.

6. Native adapters with honest limits

Paseo first

Use the supported CLI for discovery and control under the current host instructions: host-specific ls --global --json and send --no-wait --json. Pass the full agent ID and use --prompt-file for the envelope.

A flat registered roster does not need exact project/workspace joins. Keep explicit scope and responsibility in registration. The earlier SDK directory proposal remains an alternative if SDK adoption is chosen later; this revision starts with the CLI.

CLI help was checked. Live acknowledgment shape, readiness, and reply behavior still need an authorized round-trip test. Never construct a shell command from message text.

herdr second

Use the local socket's snapshot and agent.prompt operations behind the same adapter interface. Require a pinned session and verified readiness before submitting new work. Begin with snapshots; events can improve freshness later.

The installed prompt help says --wait can match the end of an already-running turn. A stall after submission does not prove that no input arrived. Keep the explicit reply contract; native waiting does not replace it.

Protocol 20 exposes agent status, readiness, pane identity, and optional session information. If a stable session cannot be established, exclude that peer until explicitly re-registered.

Use one non-overlapping background refresh loop, with a configured interval and maximum observation age. Failed refreshes make presence stale; one failed host must not disable healthy hosts. Registration preserves known ownership, but stale presence always blocks automatic delivery. Readiness checks and router reservations cannot prevent a human or another tool from concurrently using a peer.

Rollout prerequisites: explicitly enable external Jev routing per scope, provision caller/peer authentication, and verify that the chosen process identity may access herdr. Credentials stay on their owning hosts. Record IDs, timings, model/policy versions, and outcomes by default; full message logging is opt-in. No terminal transcripts are needed for routing.

7. Build in complete, testable slices

  1. Directed request and reply

    One local Paseo peer, A2A endpoint, CLI, receiver reply integration, and durable receipts. No Jev call yet. Exit when a request completes through the real sender/receiver path and the result remains readable after a router restart.

  2. Unaddressed routing

    Add the registered roster and one Jev Choice. Evaluate clear ownership, overlapping roles, no match, missing context, and an unavailable owner. Record routing accuracy, abstention rate, wrong automatic deliveries, and stage timings. Enable automatic dispatch only after the selected threshold passes the agreed examples.

  3. herdr and remote peers

    Prove a herdr round trip through the same task contract. Then verify remote authentication and the return path before enrolling remote Paseo peers. Add subscriptions, streaming, or service supervision only when actual usage requires them.

Acceptance checks for the implementation
  • Addressed requests and replies make zero Jev calls; unaddressed requests select only an authorized peer or abstain.
  • Concurrent duplicate IDs produce one task and at most one adapter attempt; changed payload under the same ID fails.
  • Crashes immediately before and after native submission never cause automatic replay of an uncertain attempt.
  • A peer disappearing, changing session, becoming busy, or going stale between selection and delivery cannot receive the request through an old registration.
  • Unrelated idle/running/blocked events cannot complete a task or impersonate a task question. Valid replies still work when discovery is stale; forged, revoked, or wrong-session replies cannot update the task.
  • Question → sender answer → final reply works on one task, with one pinned recipient. A reply arriving before the send acknowledgment remains authoritative.
  • Two answers to one question cannot both be delivered. A delayed reply to an earlier message cannot acknowledge a newer answer, complete its exchange, or release its reservation.
  • A late callback can add evidence through its control-message receipt; an ordinary A2A continuation addressed to a terminal task is rejected. Final results remain readable as artifacts.
  • Jev outage, router restart, sender disconnect, disk failure, and a late reply have explicit outcomes that the CLI displays truthfully.

Instrument receipt, routing decision, adapter acknowledgment, explicit start, and final reply. Separate transport time from recipient work. Jev's speed is accepted from the earlier user testing; this is integration measurement, not a new model-comparison prerequisite.
