An always-on Jev router for Paseo and herdr agents

A background process listens on one A2A endpoint. It keeps a live list of the Paseo and herdr agents and asks Jev which one each message is for. Then it delivers the message through that system's own interface. The only model in the loop is Jev, and code decides what happens with Jev's answer.

Verifiedchecked against docs, installed CLI or schema this session Inferredengineering reasoning from verified facts Unverifiedstill open

Recommendation

  1. Build the router as a long-running service, not an LLM agent. Its only model call is one Jev request per unaddressed message.
  2. Use A2A only at the router's front door, as the one contract that spans Paseo and herdr. Don't wrap each agent as its own A2A server.
  3. Behind the front door, one adapter per system. Paseo uses its SDK; herdr uses its socket API.
  4. Measure before building everything. Phase 0 timestamps one real exchange. Phase 1 ships the router with only the Paseo adapter and a command-line entry point.

1. Goal, current state, desired behavior

Goal

Speed up agent-to-agent messaging when agents run under Paseo or herdr. Senders shouldn't have to know which agent should receive a message.

Today

Every sender follows the paseo-a2a skill. It keeps its own list of peers, runs discovery commands, writes an envelope and delivers it. For terminal peers it also checks the terminal is idle, sends the text, and reads back output between start/end markers.

Desired

A sender makes one call: route "<message>", or an A2A SendMessage. The router picks the recipient, delivers, tracks the task, and sends the reply back to whoever asked.

2. The logic: where the time goes

This is the core argument, so here is the chain of reasoning. Sending a message has four stages. Only some of them can be made faster by routing, and delivery is not the slow one.

StageTodayCan we speed it up?Who fixes itBasis
Decide recipient Sender LLM runs paseo ls / inspect / terminal ls and reads the JSON. Each step is a full LLM turn. Yes, and it's the biggest cost Router directory + Jev Inferred from the discovery steps the skill requires
Deliver paseo send returns once the daemon accepts the message. Barely; it's already fast — Verified SDK send() resolves when the daemon accepts it (earlier research)
Terminal handshake Check the terminal is idle and nobody else is typing, send the text and Enter separately, then read output between PASEO_A2A_START/END markers. Yes herdr adapter Verified herdr's agent.prompt refuses to send if the agent is blocked, reports a stall after 5 s, and --wait waits for the agent to settle

What follows: the time we can save is in deciding and in the terminal handshake, not in the transport. That's why the design pairs a classifier (Jev) with an adapter that knows the agent's state (herdr), rather than a faster wire protocol. 5. Decisions and the evidence behind them

D1 · The router is a service, not an LLM agent

Reasoning. Keeping it always on is right: the directory stays warm, and the Paseo and herdr connections are already open when a message arrives. But the thing that stays running should be a normal process. Stage 1 in §2 is slow because an LLM is deciding; an LLM router would just move that delay rather than remove it.

Evidence. Verified Jev returns an answer plus probabilities, not text. The API is POST https://api.typesafe.ai/v1/systemone with model jev-latest, and Choice answers contain choice, probabilities and confidence. Unverified The docs give no latency figure, and I haven't measured one. Like the earlier research, this relies on your own testing.

D2 · Jev picks, code decides

Reasoning. Jev chooses from options the router gives it and returns a probability for each. Everything with consequences stays in code: whether to send, whether to escalate, who's allowed to receive. So a message can't instruct the router to do anything; the worst it can do is make Jev pick a different peer from the approved list.

Evidence. Verified A Choice question can have up to 255 options, which covers any realistic set of peers. Several questions in one request "barely" change response time. The confidence docs suggest acting automatically above ~0.9, confirming between 0.5 and 0.9, and escalating below 0.5, and say to start conservative and tune on your own data.

D3 · A2A only at the front door

Reasoning. A2A gives both systems one shared set of terms: an Agent Card describing an agent, task IDs, task states, and a way to stream updates. If the router is the only A2A server, that costs one hop in total rather than one per agent, and outside agents can connect later without changes. Behind the front door, the adapters speak Paseo and herdr directly.

Evidence. Verified A2A spec v1.0 runs over JSON-RPC 2.0, gRPC or HTTP+JSON. Task states are SUBMITTED → WORKING → COMPLETED | FAILED | CANCELED | REJECTED, plus INPUT_REQUIRED and AUTH_REQUIRED. It describes point-to-point transport with no routing and no local/IPC binding. The official @a2a-js/sdk v1.0 has both server and client for all three transports. Inferred Because there's no IPC binding, local agents will reach the front door either over HTTP on localhost or through a small route command that speaks A2A.

D4 · One adapter per system, using its own interface

Paseo adapter

  • Uses one @getpaseo/client connection per configured host. The directory design from paseo-directory-design.md carries over unchanged. Verified
  • Keeps its view current via list({subscribe:{}}) for agents and workspaces; terminals have to be re-listed periodically. Verified (earlier research)
  • Reaches other hosts. Unverified the MBA endpoint and live SDK responses.

herdr adapter

  • Connects to the local socket at ~/.config/herdr/herdr.sock (protocol 20, herdr 0.8.2). Verified
  • Keeps the directory current by subscribing to events.subscribe for pane_agent_detected and pane_agent_status_changed, so no polling. Verified in the schema
  • Each agent record includes name, agent, agent_status, cwd, pane_id and interactive_ready. Verified in the schema
  • Delivers with agent.prompt, which refuses to send to a blocked agent. That replaces the start/end marker protocol. Verified
  • Only works on the machine running herdr; --remote is an SSH attach. Inferred The router should therefore run on the same machine as herdr.

D5 · Senders call the router explicitly, and addressed messages skip Jev

Reasoning. Having the router watch terminal output and guess which messages are meant for another agent would be slow and fragile. Instead, a sender makes one deliberate tool call. If it already names a recipient (a reply, or a message from a parent to its child), the router goes straight to the adapter with no Jev call. Jev only runs when the recipient is unknown, which is where it saves LLM turns.

Evidence. Inferred from §2: nothing needs deciding for addressed messages.

7. Jev request sketch

A single request with three questions. Each peer's description (its "card") becomes that Choice option's criteria text, so the quality of those descriptions directly limits routing accuracy. Written to the Verified API shape. The peer names and the question wording are illustrative. 

POST https://api.typesafe.ai/v1/systemone
Authorization: Bearer $TYPESAFE_API_KEY

{
  "model": "jev-latest",
  "state": {
    "message": { "from": "paseo:mba/agent:3f2c…", "text": "…" },
    "peers_note": "Options are the live, eligible peers only."
  },
  "questions": {
    "recipient": {
      "type": "choice",
      "instructions": "Which peer should handle `message.text`?",
      "criteria": {
        "reviewer": "herdr:reviewer — Codex; reviews diffs in jev-a2a, reports findings only",
        "builder":  "paseo:mba/agent:9a1e… — Claude; implements features in paseo-plugin",
        "none":     "No listed peer owns this; a human should decide"
      }
    },
    "intent": {
      "type": "choice",
      "instructions": "What kind of message is `message.text`?",
      "criteria": {
        "request": "asks someone to do work",
        "result":  "reports finished work",
        "question":"asks for information or a decision",
        "blocked": "the sender cannot continue without help"
      }
    },
    "escalate": {
      "type": "noul",
      "instructions": "Does `message.text` need a human decision (permissions, destructive action, credentials, scope change)?"
    }
  }
}

Keys such as reviewer are stand-ins for the directory keys (host, channel, id). Code maps the answer back to a live directory entry just before sending, so a choice made against an old snapshot can't deliver to a peer that has since disappeared.

8. Routing policy (code)

Starting thresholds come from TypeSafe's confidence guidance and are meant to be tuned on logged traffic. Inferred

ConditionActionWhy
escalate ≥ 0.5 or intent = blockedEscalate to you. Don't auto-deliver.Permissions and destructive actions are never the router's call (the paseo-a2a ground rules).
recipient = noneEscalateSaying "I don't know" is a useful answer, and the router never broadcasts.
confidence ≥ 0.9DeliverHigh confidence (TypeSafe guidance).
0.5 ≤ confidence < 0.9Ask the sender or you to confirm the top one or two picksMedium band. Only send to two peers at once if both agree to it.
confidence < 0.5EscalateLow confidence.
Picked peer is stale, gone or blockedDon't send. Refresh the directory and retry once, then escalate.Carried over from the earlier directory design's rules on stale snapshots.
Hop count > N, or a message with the same ID has already been routedDrop it and reportStops agents bouncing messages back and forth forever.

9. Task states

The router keeps a table of tasks keyed by task ID. A2A task states are what senders see. The mapping below is Inferred. Note that an agent going idle is not the same as the task being done: a task completes only when the recipient sends its reply back through the router.

A2A statePaseo signalherdr signal
SUBMITTEDsend() accepted by the daemonagent.prompt returned without error
WORKINGagent status is runningpane_agent_status_changed → working
INPUT_REQUIREDa pending permission requestblocked (an approval or question dialog)
COMPLETEDa reply arrives at the router carrying this task ID
FAILEDsend error, or no reply before the timeoutagent_prompt_stalled, agent_blocked, or a timeout

10. Risks and failure modes

  • Message text leaves the machine. Every unaddressed message is sent to api.typesafe.ai. Decide whether that's acceptable for your repos, and remove secrets before the Jev call. The paseo-a2a skill already bans credentials in messages.
  • Router is down. Senders fall back to the existing paseo-a2a direct routes, so messaging gets slower but keeps working. The skill needs a line saying so.
  • Routing is only as good as the peer descriptions. Agent titles alone may not tell peers apart. Add explicit one-line role descriptions per peer; the router must never guess a role from what's on a terminal screen.
  • Prompt injection. Message text is untrusted data. Jev can only choose from the approved list, and the router never acts on what a message says.
  • herdr access from a service. The herdr skill's HERDR_ENV check is meant for agents running inside panes. A service connecting to the socket directly is a separate choice, and it's your call to allow it.
  • Jev rate limits and outages (429/529). Retry with exponential backoff, as the API docs advise, and escalate if it keeps failing; never guess a recipient.
  • Directory lists aren't taken at one instant. Separate list calls can disagree, so leave unresolved placements unresolved. This carries over from the earlier research.

11. Rollout

  • Phase 0 · Measure. Timestamp one real exchange: decide recipient, discover, send, recipient starts, reply. This confirms or refutes §2.
  • Phase 1 · Router, Paseo adapter, route CLI. In-memory directory, one Jev request per message, the policy table, the task table. Log every Jev answer to tune thresholds later.
  • Phase 2 · herdr adapter. Socket subscription feeds the directory; delivery via agent.prompt; blocked → INPUT_REQUIRED.
  • Phase 3 · A2A front door. Serve the Agent Card with @a2a-js/sdk, and rewrite route as a thin A2A client.
  • Phase 4 · Tuning. Adjust thresholds from the logs; add Paseo live subscriptions where polling is too slow.

13. Open questions

  1. Which machine runs the router? It must be the one with the herdr session, and it must be able to reach every Paseo host.
  2. Is sending message text to TypeSafe acceptable for all repos, or only for some?
  3. Should the front door be HTTP bound to localhost only, or also reachable from your other machines? That decides whether A2A authentication is needed from day one.
  4. Who writes the peer role descriptions: the agent itself at startup, you, or a registration step?
  5. Should the router service be allowed to talk to the herdr socket from outside a herdr pane?
